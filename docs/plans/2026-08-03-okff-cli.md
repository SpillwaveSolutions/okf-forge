# `okff` — a shell launcher for OKF Forge

## Goal

`okff [directory]` opens OKF Forge on that folder from any terminal. The shim is
installed from a new Settings view inside the app, the way VS Code installs `code`.

## Why a shim and not a symlink

`OKFForge.app` is a bundle; the executable inside it is not runnable standalone —
launching `Contents/MacOS/okfforge` directly gives no dock icon, no bundle
identity, and no LaunchServices activation. `open` is the supported entry point,
so the thing on PATH has to be a script that calls it.

## Design

### The shim

Written to `/usr/local/bin/okff`, which is already on the default macOS PATH —
that is what makes the user's stated requirement ("it should be on the path")
actually hold without a shell-rc edit.

```sh
#!/bin/sh
case "${1:-}" in
  -h|--help) echo "usage: okff [directory]"; exit 0 ;;
esac
dir=$(cd "${1:-.}" 2>/dev/null && pwd) ||
  { echo "okff: no such directory: $1" >&2; exit 1; }
open -n -b com.okf.forge --args --workspace "$dir" ||
  open -n "__APP_PATH__" --args --workspace "$dir"
```

Resolution is **bundle id first**, absolute path second. Moving or reinstalling
`OKFForge.app` breaks a hardcoded path; it does not break a bundle-id lookup.
The path is baked in only as a fallback for the case where LaunchServices has
not registered the bundle yet.

`-n` opens a new instance per invocation, which is the chosen behaviour: two
folders, two windows.

### Rust — argv

`run()` scans `std::env::args()` for `--workspace <path>` before building, and
seeds the existing `WorkspaceState` mutex with the canonicalized result. macOS
passes `-psn_0_…` to GUI launches, so unknown arguments are ignored rather than
treated as the path. An invalid path is ignored too — the app opens on the
sample rather than refusing to start, because a desktop app that dies on a bad
argument with no terminal attached looks like a crash.

### Rust — install

Two commands:

- `cli_status() -> { installed, path, managed, on_path }` — reads
  `/usr/local/bin/okff` if present. `managed` means the file carries our marker
  comment, so a hand-rolled `okff` the user wrote themselves is never silently
  overwritten.
- `install_cli() -> String` — writes the shim to a temp file, then moves it into
  place. If `/usr/local/bin` is writable (common with Homebrew) it is a plain
  copy with no prompt. Otherwise it escalates once through
  `osascript -e 'do shell script "…" with administrator privileges'`, which is
  the same single admin prompt VS Code shows.

`uninstall_cli()` for symmetry — an installer with no uninstaller is a thing
users resent.

### Frontend

`init()` already ends by loading the bundled sample. Before that, when running
under Tauri, it asks `storage.getWorkspaceRoot()`; a non-null answer means the
CLI seeded a workspace, and the existing `loadWebWorkspace()` path loads it.
That function is misnamed for its new second caller — it is runtime-agnostic and
goes through `getStorage()` — so it is renamed `loadStorageWorkspace`. **No new
IPC command is needed for the workspace half of this feature.**

New `settings` view, 8th nav item. In web builds the card explains the CLI is
desktop-only instead of offering a button that cannot work.

## Cost outside the feature

The nav order appears in the element inventory of all seven existing view specs,
and the inventory is a merge gate. Seven specs get one line each, plus a new
`ui-settings.md` + `.puml` + rubric, plus a row in `e2e/views.spec.ts`.

## Testing

| Tier | Covers |
|---|---|
| vitest | shim text generation — quoting, help case, path with spaces |
| node:test | `--workspace` argv parsing, mirrored from the Rust logic |
| cargo | argv parsing, shim rendering, `cli_status` on a temp dir |
| Playwright | settings view renders; 8 nav items; existing 3 view gates extend |
| by hand | `okff .` in a real shell opens a real window on the real folder |

The hand check is the one that matters. Nothing automated can prove a shim on
`/usr/local/bin` launches a bundle.

## Known gap, recorded not hidden

Two instances share one localStorage origin. Changing the theme in window A does
not reach window B until B reloads, and zoom is last-write-wins. This is the
accepted cost of the multi-instance choice; it goes in the Settings spec's
Known gaps section.
